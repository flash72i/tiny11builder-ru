# Аудит и русификация Tiny11 Builder WinUI 0.1.1 — технический отчёт

**Исходный релиз:** [ntdevlabs/tiny11builder · winui-v0.1.1](https://github.com/ntdevlabs/tiny11builder/releases/tag/winui-v0.1.1) (commit `d060813`)

## 1. Аудит: что за программа и где живёт её текст

### 1.1 Состав релиза
Релиз — два ZIP (x64 и ARM64) с **self-contained** публикацией .NET 8 + Windows App SDK 2.5.1 (WinUI 3, распакованный режим, `WindowsPackageType=None`). Контрольные суммы ZIP сверены с опубликованными `.sha256` — совпали.

Ключевые файлы приложения (543 файла в архиве, остальные — рантайм .NET/WinUI):

| Файл | Роль |
|---|---|
| `Tiny11Builder.exe` | нативный apphost (загрузчик .NET), интерфейсных строк нет |
| `Tiny11Builder.dll` (334 КБ) | основная сборка: `MainWindow.xaml.cs`, `Choices.cs`, `OperationFlow.cs` — диалоги, статусы, уведомления, сценарии отмены |
| `Tiny11Builder.Core.dll` (368 КБ) | движок сборки: DISM-операции, каталог удалений (`CleanupCatalog`, `PolicyCatalog`), загрузчик ISO, чекпоинты, отчёты |
| `Tiny11Builder.pri` (2,2 МБ) | пакет ресурсов MRT (`mrm_pri2`), внутри — **скомпилированный XAML** (`MainWindow.xbf`, 31 КБ) со всеми текстами разметки |
| `Tiny11Builder.deps.json` | манифест зависимостей (TPA-список хоста) |

### 1.2 Где физически находятся строки интерфейса
Программа **не использует .resw/ResourceLoader** — локализационной инфраструктуры нет. Весь текст распределён по трём хранилищам:

1. **XAML-литералы → XBF внутри `.pri`** (158 отображаемых значений: `Text=`, `Content=`, `Header=`, `PlaceholderText=`, `OnContent/OffContent`, `Title/Message` у InfoBar, `AutomationProperties.*`). XBF — закрытый бинарный формат, лежит внутри бинарного же PRI-контейнера со смещениями/индексами.
2. **Строковые литералы IL (`#US`-куча) в `Tiny11Builder.dll`** — 632 литерала: уведомления, диалоги отмены, тексты результатов, метки.
3. **Строковые литералы IL в `Tiny11Builder.Core.dll`** — 1366 литералов: названия/описания ~40 опций удаления, сообщения этапов, ошибки, предупреждения отчёта.

Исходный код приложения открыт (тот же тег на GitHub), что позволило сверить каждый литерал с контекстом его использования.

### 1.3 Критические строковые связи (главный риск русификации)
Аудит выявил, что часть строк — **не только текст, но и ключи логики**:

* **Имена этапов** (`"Copy media"`, `"Commit"`, `"Cancel cleanup"`…) одновременно: (а) отправляются движком в прогресс, (б) сравниваются в `BuildProgressText.Phase()/Range()` (шкала 0–100% и разбиение на 7 фаз истории), (в) в App с константой `CancelCleanup.Stage` маршрутизируется диалог отмены.
* **Категории опций** (`"Bundled apps"`, `"Optional features"`, `"Windows settings"`, `"Advanced / original builder"`, `"All"`) сравниваются с содержимым ComboBox фильтра (`o.Category == category`).
* **Статусы этапов** (`"Complete"`, `"Done earlier"`) сравниваются в `StageSummary.IsDone` (счётчик «N из 7 этапов»).
* **Префиксы журнала** (`"Plan payload: "`, `"Removing payload: "`, `"Payload removed: "`) — по ним `BuildOperationTracker` определяет состояние операций.

## 2. Метод русификации

Единый мастер-словарь **1021 запись** (`translations_master.py`), из него три набора:

| Набор | Записей | Механизм применения |
|---|---|---|
| App IL (`Tiny11Builder.dll`) | 372 ключа | замена операндов `ldstr` (Mono.Cecil) — **441 инструкция** |
| Core IL (`Tiny11Builder.Core.dll`) | 522 ключа | то же — **608 инструкций** (+44 сохранены, см. 2.2) |
| XAML-словарь | 147 пар | новый модуль `Tiny11Builder.Ru.dll`: обход дерева элементов окна и замена текстовых свойств по точному совпадению |

### 2.1 XAML: рантайм-слой вместо правки XBF/PRI
XBF и MRT PRI — недокументированные бинарные форматы со взаимными смещениями; пересборка «вслепую» (без возможности запустить WinUI в песочнице) дала бы неоправданный риск нерабочего приложения. Рантайм-перевод:
* компилируется на Linux против **тех же** проекционных сборок WinUI из релиза (`Microsoft.WinUI 3.0`, `WinRT.Runtime 2.2`) — корректность API подтверждена компилятором;
* внедряется одним вызовом `RuLocalization.Attach(this)` в конец `MainWindow..ctor` (до `Activate()` — пользователь не видит английский текст);
* покрыт `try/catch` целиком: при любом сбое приложение продолжает работать (английский XAML — деградация, но не отказ);
* идемпотентен, повторно применяется по `Loaded` + 15 тиков таймера 400 мс (страховка для поздно материализуемых элементов);
* переводит: `TextBlock.Text`, `ContentControl.Content`, `TextBox/ComboBox/ToggleSwitch.Header`, `PlaceholderText`, `OnContent/OffContent`, `InfoBar.Title/Message`, `Expander.Header`, `AutomationProperties.Name/HelpText/FullDescription/ItemStatus`, `ToolTip`, включая нераскрытые пункты ComboBox/ListView (обход `Items`).

### 2.2 IL: замена литералов + защита компиляторных деревьев (ключевая находка)
Прямая замена `ldstr` сломала бы два механизма, что **выявила симуляция** (раздел 3):

1. **Деревья переключения строк.** Roslyn компилирует `switch`-выражения по строкам (`BuildProgressText.Phase/Range`, фильтр этапов в `BuildAsync`) в деревья маршрутизации **по длине строки и кодам символов** (`get_Length`+`switch`, `get_Chars`), и лишь в листьях сравнивает строки целиком. Замена литералов leaves оставляет маршрутизацию английской → все русские имена этапов получали phase=-1. **Решение:** в трёх таких методах литералы сохранены английскими, а на входе внедрён префикс-нормализатор `<RuPatch>.MapStage(string)` (20 пар RU→EN, сгенерирован Cecil'ом). Итог: `Phase/Range` принимают **и русские, и английские** имена этапов и возвращают идентичные результаты (проверено зондом: 20/20 совпадений, неизвестный ввод → безопасный -1).
2. **UTF-8 литералы `u8` (FieldRVA).** `"MSWIM\0\0\0"u8` хранится не в `#US`, а в инициализируемых данных поля (FieldRVA). При «ленивом» чтении Cecil терял эти данные → проверка WIM-заголовков отвергала бы **любой** образ. **Решение:** принудительная материализация `FieldRVA` перед записью; наличие байтов `MSWIM` и корректность подтверждены (тесты реальных DISM-заголовков 7/7).

Per-assembly словари решают конфликт омонимов: `Start` в App — кнопка «Начать», в Core — имя значения реестра службы (не переводится); `The ` в App — артикль (схлопнут), в Core — «Папка {имя} не может быть удалена».

Единство перевода обеспечено общим словарём: одна английская строка → одна русская во всех наборах (этапы, категории, статусы, «Cancel safely» ↔ кнопка и тексты, префиксы журнала ↔ их матчинг).

**Инъекция зависимостей:** `AssemblyRef Tiny11Builder.Ru 0.1.1.0` + запись в `Tiny11Builder.deps.json` (targets/libraries/dependencies) — хост добавляет DLL в TPA.

## 3. Верификация (симуляция корректности)

1. **Контрольные суммы** оригинальных ZIP совпали с опубликованными (x64 `DA74C179…`, ARM64 `29C5D96B…`).
2. **Покрытие XAML: 158/158** отображаемых значений — переведены или сознательно сохранены (бренды, `SHA-256`, `.NET Framework 3.5`, значения ComboBox компонентов, сверяемые с `Enum.ToString()`: `ProvisionedApp`, `SystemApp`, `Feature`, `Capability`, `Package`, `Service`, `ComponentPayload`).
3. **Покрытие IL:** обратная проверка — все «человекочитаемые» строки обеих сборок либо в словаре, либо в явном списке KEEP (переменные окружения, форматы дат, id пакетов, языки каталога MS, DISM-состояния и т.п.).
4. **Валидность метаданных:** полное чтение IL обеих сборок Cecil — **2454 метода** (2453 + `MapStage`), ошибок нет; `#US`-контроль: 0 непереведённых ключей, 364 кириллических строки в App, 521 в Core; хук `Attach` на месте (дизассемблирование `.ctor`); AssemblyRef корректен.
5. **Инварианты целостности** (обе архитектуры): 20 русских ключей этапов присутствуют в эмиссии; английские ключи сохранены только внутри деревьев `Phase/Range/b__14`; `Cancel cleanup`/`Очистка после отмены` согласованы App↔Core; regex'ы, DISM-состояния, `Package Identity`, `Windows 11 Pro`, языки MS-каталога, реестровые `Start/Type/Select`, внутренние id — не тронуты; пути привязок XBF не затронуты (PRI не менялся).
6. **Зонд `Phase`/`Range` на реальной пропатченной сборке:** все 20 этапов — русский ввод == английский ввод == ожидаемые фаза и диапазон (0–8, 8–15, …, 98–100); неизвестная строка → -1.
7. **Дифференциальные юнит-тесты** (штатный набор репозитория, 336 тестов, исполняют реальный `BuildEngine` с эмулятором DISM), три стенда на Linux:
   * **A** — оригинальные бинарники + английские исходники логики App;
   * **B** — ПРОПАТЧЕННЫЕ бинарники + русифицированные исходники логики App (точная копия поставки);
   * **C** — как B, но и сами тесты механически переведены тем же словарём («полностью русскоязычный продукт»).

   | Показатель | A | B | C |
   |---|---|---|---|
   | Пройдено | 187 | 125 | 148 |
   | Провалено (всего) | 149 | 211 | 188 |

   Провалы A — среда Linux (Windows API, пути `C:\`, backslash-фикстуры): они идентичны в B и C. **Каждый** из 62 «новых» провалов B и 39 «новых» провалов C разобран по сообщениям:
   * B: 100% — утверждения, ожидающие английский текст (продукт выдаёт корректный русский);
   * C: 100% — артефакты машинного перевода самих тестов (ожидаемые подстроки/префиксы остались английскими либо собраны из непереведённых фрагментов, например `StartsWith("Отмена")` против продуктового `Отменить сборку`, `Contains("build 26201")` против `«Этот образ — сборка 26201»`);
   * **ни одного поведенческого/логического отличия не обнаружено.**
   * Показательные классы: `WimHeaderTests` — C: 7/7 PASSED (как A; бинарная валидация WIM + FieldRVA intact), `OperationTests` — C == A (2/12, шкалы диапазонов), `CompatibilityTests` 42/42 PASSED во всех трёх, `DownloaderTests` 12/12 PASSED во всех трёх.

### Известные допущения и ограничения
* у двух пропатченных DLL снят Win32-ресурс VERSIONINFO (обход бага Cecil при записи native-ресурсов .NET 8; на работу не влияет; свойства EXE не тронуты);
* приложение не подписано (как и оригинал) — SmartScreen может предупреждать;
* русские строки длиннее английских — вёрстка WinUI (переносы/авторазмер) компенсирует, в редких местах текст может занять больше строк;
* чекпоинт сборки, созданный английской версией, русская не возобновит (и наоборот) — внутренние ключи фаз в `checkpoint.json` не переводятся, но сообщение об отказе корректно; начатую сборку продолжайте той же версией приложения;
* вывод самого DISM/oscdimg в журнале остаётся английским (это текст внешних инструментов Windows).

## 7. Дополнение rev.3 (15.10.2026) — по отзыву с реальной машины

Журнал пользователя за rev.2 (`attach end ok in 60 ms`, 174 замены, 843 узла/проход) подтвердил:
зависание устранено, обход линейный. Выявлены и исправлены два дефекта отображения данных:

### 7.1 Пустой список групп удаления (шаг «Компоненты»)
Первопричина (MainWindow.xaml.cs:807-808): `FilterOptions()` сравнивает текст выбранного пункта
ComboBox (`category`) с литералом `"All"` и с `o.Category`. В rev.2 литерал в IL заменён на «Все»,
а текст пункта переводился рантайм-слоем; первый вызов `FilterOptions()` происходил в конструкторе
окна РАНЬШЕ перевода текстов → `category=="All"` (англ.) против литерала «Все» → все категории
отфильтрованы в пустоту. Исправление: хук `RuLocalization.Attach` внедрён в `MainWindow..ctor`
сразу ПОСЛЕ `InitializeComponent()` (подтверждено дизассемблированием: ctor[76] InitializeComponent,
ctor[78] Attach) — перевод текстов предшествует любой логике, читающей эти тексты.

### 7.2 «Иероглифы» в именах редакций образа
Первопричина (ProcessRunner.cs:20-24): `ProcessStartInfo` создаётся без `StandardOutputEncoding`;
.NET декодирует перенаправленный stdout дочернего процесса кодовой страницей консоли/ANSI (CP1251
в русской Windows), тогда как dism.exe печатает не-ASCII-имена в OEM (CP866) → мусор вида «˛®¬ ипп».
Дефект ВЕРХНЕГО уровня: в оригинале 0.1.1 он же (на английских системах незаметен — имена ASCII).
Исправление в русской сборке: в `ProcessRunner/<RunAsync>d__0::MoveNext` внедрена установка
`StandardOutputEncoding`/`StandardErrorEncoding` = `Encoding.GetEncoding(CultureInfo.CurrentCulture
.TextInfo.OEMCodePage)` перед `BeginOutputReadLine()` (подтверждено: MoveNext[70] get_OEMCodePage,
[75]/[78] set_Standard*Encoding). Корректно для любой языковой системы (OEM=866/437/…).
